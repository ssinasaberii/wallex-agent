# Data Architecture and Caveman Context Policy

**Version:** 1.1  
**Status:** Architecture approved; integration unverified  
**Context optimizer:** Caveman Engine / Proxy

## 1. هدف

تهیه داده معتبر، تازه و مرتبط برای:

- موتور کمی تولید فرصت
- فیلترهای خبری و رویدادی
- Jev Entry Confirmation
- موتور قطعی ریسک
- سیستم ممیزی تصمیم‌ها

## 2. اصل معماری

داده خام بازار ابتدا توسط کد پردازش می‌شود. Jev نباید دفتر سفارش کامل، صدها معامله خام یا محاسبات مالی را به‌صورت متن دریافت کند.

مسیر اصلی:

`Market Data → Validation → Quantitative Features → Candidate → Context Builder → Jev`

## 3. منابع داده

### Wallex

- فهرست بازارها
- وضعیت بازار
- دفتر سفارش
- معاملات اجراشده
- کندل
- موجودی
- سفارش‌های باز
- کارمزد واقعی برای هر بازار و نرخ Maker/Taker از حساب تأییدشده
- موجودی آزاد اسپات و سفارش‌های باز جهت محاسبه ده جایگاه خرید
- محدودیت حداقل ارزش سفارش (`minNotional`, `minQty`, `stepSize`, `tickSize`)
- وضعیت حساب اعتباری

### External Sources

- اخبار معتبر
- اطلاعیه‌های رسمی
- تقویم Macro
- نرخ تبدیل معتبر برای برآورد تومانی سفارش‌های بازارهای غیرتومانی

## 4. Market Discovery

بازارها توسط الگوریتم قطعی فیلتر و رتبه‌بندی می‌شوند.

مراحل:

1. حذف بازارهای غیرمجاز
2. حذف بازارهای غیرفعال
3. بررسی نقدشوندگی
4. بررسی اسپرد
5. بررسی کیفیت داده
6. رتبه‌بندی کمی
7. انتخاب حداکثر سه بازار برای بررسی عمیق در هر چرخه تحلیل اولیه؛ **این محدودیت با سقف ۱۰ موقعیت خرید باز متفاوت است** و مانع بررسی متناوب بازارهای دیگر نیست

**Jev در Market Discovery نقشی ندارد.**

## 5. Context Builder

وظایف:

- استخراج فقط شواهد مرتبط با کاندیدای مشخص
- حفظ شناسه کاندیدا
- حفظ زمان داده
- خلاصه‌سازی وضعیت سیگنال‌ها
- معرفی تعارض‌ها
- ثبت اطلاعات ناموجود
- افزودن خبر مرتبط و تأییدشده
- افزودن نتیجه محاسبه کارمزد و افق اقتصادی، بدون ارسال جزئیات حساب و شناسه محرمانه
- ثبت تعداد جایگاه‌های خرید اشغال‌شده و ظرفیت ده‌تایی

خروجی باید کوتاه، ساختاریافته و قابل‌بازتولید باشد.

## 6. نقش Caveman

Caveman Engine / Proxy فقط برای Contextهای متنی مناسب استفاده می‌شود.

### کاربردهای مجاز

- متن خبرهای طولانی
- چند اطلاعیه مرتبط
- خروجی متنی ابزارهای تحقیق
- گزارش‌های تکراری
- Contextهای دارای تکرار زیاد

### کاربردهای ممنوع در MVP

- تغییر یا تقریب قیمت
- تغییر حجم سفارش
- تغییر زمان
- تغییر کارمزد
- تغییر حداقل ۱۰۰٬۰۰۰ تومان یا محدودیت رسمی سفارش
- تغییر نرخ تبدیل تومانی و قیمت اجرایی سفارش فروش
- تغییر موجودی
- حذف شناسه سفارش
- فشرده‌سازی غیرقابل‌بازیابی اطلاعات ریسک

## 7. مسیرهای مستقل

### مسیر استاندارد

`Structured Context → Jev`

### مسیر اختیاری

`Long Text → Caveman → Recovered/Compressed Context → Jev`

مسیر دوم فقط پس از تأیید سازگاری با API Jev فعال می‌شود.

## 8. Data Freshness

هر رکورد باید:

- source
- event_time
- received_time
- processed_time
- quality_status

داشته باشد.

تازگی داده باید متناسب با **پنجره انتخاب‌شده، حجم معاملات بازار، افق اقتصادی، و تأخیر API** تعیین شود. آستانه ثابت پنج‌ثانیه‌ای برای همه بازارها و افق‌ها الزام‌آور نیست؛ Snapshot کارمزد نیز زمان اعتبار مستقل دارد و با تغییر آن باید کاندیدا بازنگری شود.

## 9. News Integrity

برای هر خبر:

- منبع
- زمان انتشار
- زمان دریافت
- دارایی مرتبط
- نوع رویداد
- وضعیت تأیید
- شناسه یکتا
- ارجاع به متن اصلی

ثبت شود. اخبار تکراری نباید چند بار به‌عنوان رویداد مستقل در تصمیم وارد شوند.

## 10. Compression Benchmark

نسخه دارای Caveman باید با نسخه بدون Caveman مقایسه شود.

معیارها:

- تعداد توکن
- هزینه واقعی
- تأخیر انتهابه‌انتها
- موفقیت بازیابی
- تغییر پاسخ Jev
- خطای حذف اطلاعات
- خطای داده حساس

### شرط فعال‌سازی

فشرده‌سازی فقط زمانی فعال می‌شود که:

- منفعت اندازه‌گیری‌شده داشته باشد.
- اطلاعات ضروری را حفظ کند.
- پاسخ‌های ایمنی را خراب نکند.
- مسیر Fallback سالم باشد.

## 11. Failure Policy

اگر Caveman خطا داد:

- داده اصلی حفظ می‌شود.
- مسیر بدون فشرده‌سازی بررسی می‌شود.
- اگر Context معتبر و به‌موقع قابل تهیه نبود، ورود انجام نمی‌شود.

Caveman نباید مسیر خروج اضطراری را تحت تأثیر قرار دهد.

## 12. Audit

برای هر تصمیم Jev ثبت شود:

- شناسه کاندیدا
- Context اصلی
- Context ارسال‌شده
- وضعیت Caveman
- نسخه مدل
- پاسخ Jev
- تأخیر
- نتیجه نهایی

## 13. اصل نهایی

**ابتدا Context درست و مختصر؛ سپس فشرده‌سازی اختیاری و قابل‌اندازه‌گیری.**

## 14. منابع مخصوص سفارش اسپات

براساس مستندات منتشرشده والکس، فهرست بازارهای اسپات از مسیر `/hector/web/v1/markets` با شرط `is_spot` شناسایی می‌شود، سفارش خرید/فروش در `/v1/account/orders` ثبت و وضعیت آن از مسیر جزئیات سفارش و سفارش‌های باز پیگیری می‌گردد. `minNotional` و دقت مقدار/قیمت باید از منبع معتبر همان بازار تأیید شوند؛ مثال‌های مستندات را نباید جایگزین مقادیر زنده کرد.

## 15. Fee Snapshot

برای هر بازار باید Snapshot شامل `symbol`, `maker_fee_rate`, `taker_fee_rate`, `source`, `retrieved_at`, `validity`, `fee_asset_rule` وجود داشته باشد. در مرجع API والکس دریافت کارمزد حساب از `GET /v1/account/fee` مستند شده است؛ در زمان پیاده‌سازی باید در حساب مخصوص چالش تأیید شود. نبود نرخ معتبر مانع ورود جدید است.

## 16. Context Window Separation

سه مفهوم مستقل هستند:

1. `Market Observation Window`: داده OBI/TFI/Momentum برای تشخیص سیگنال؛ از افق اقتصادی مشتق می‌شود.
2. `Expected Holding Horizon`: زمانی که دامنه حرکت محافظه‌کارانه می‌تواند هزینه معامله را پوشش دهد؛ وابسته به کارمزد واقعی است.
3. `News/Context Retrieval Window`: بازه دریافت خبر برای توضیح تصمیم؛ نباید با دو مورد بالا یکی فرض شود.

Caveman صرفاً روی Context متنی مناسب تأثیر می‌گذارد و هیچ‌کدام از محاسبات عددی فوق را انجام نمی‌دهد.
